RULE DISCOVERY PIPELINE

에디팅 규칙 발굴 기본 4단계

각 단계는 저장 가능한 데이터 작업 Job이며, 개별 검증 또는 M04001 통합 Flow 실행이 가능합니다. 아래 탭은 현재 도움말과 구현 객체를 기준으로 입력, 처리, 출력과 해석 포인트를 정리합니다.

1
M03001 · UNIFIED_EDITING_PROFILE

컬럼 유형 분석

기존 컬럼 유형 판정과 사용자 확정값 보존을 유지하면서 표본 기초통계·숫자 문자열·변환 불가 값 진단을 보강합니다. 아래 규칙·모델 결합은 기존 Oracle 하위 분석이며, 보강 진단은 원본 자료형과 최종 유형을 변경하지 않습니다.

프로파일·규칙 입력

  • 데이터 타입, NULL, DISTINCT 개수와 전체 행 대비 비율
  • 최소·최대, 길이, 소수·정수 비율, 수치 변환 비율
  • 엔트로피·값 분포와 컬럼명 의미 힌트
  • 예측 방식, 샘플, 신뢰도와 Target DB 활성 모델

현재 규칙 판정

  • INIT$_FN_PREDICT_BASE_TYPE_V3가 식별자·연속·이산·순서·범주·텍스트 유형을 판정
  • INIT$_FN_PREDICT_BASE_REASON_V3가 판정 근거를 설명
  • 숫자 데이터 타입만으로 연속형을 단정하지 않음

Rule + Model 최종 선택

  • 규칙·모델 일치, 한쪽 결과 누락, 신뢰도와 그룹 호환성을 평가
  • 연속형→범주형 오분류 차단, 식별자·자유 텍스트 보호
  • 모델 판단 로직 자체는 변경하지 않고 최종 호환성 가드에서 조정

출력·후속 단계

  • 이번 Run의 RULE·MODEL·FINAL 유형과 판정 사유
  • 사용자 확정값을 보존한 최신 최종 유형
  • M03002 관계 분석의 유형 기준
UNIFIED_EDITING_PROFILE → PREDICTED_TYPE_RUN · PREDICTED_TYPE_FINAL · MIXED_XAI_PROFILE
2
M03002 · UNIFIED_EDITING_RELATION

컬럼 상관·관계 분석

기존 최종 유형 기준의 관계 행렬·네트워크·군집을 유지하고, 별도 표본에서 수치 상관·범주 관계·상관비 η와 결측·중복을 진단합니다. 기존 관계의 통과 기준과 혼합형 표본 진단을 구분해 해석합니다.

유형별 지표

  • 범주형×범주형: Cramér's V와 p-value
  • 연속형×연속형: Pearson, 선택 시 Spearman과 p-value
  • 범주형×연속형: Eta Squared

네트워크·군집

  • 실제 Run 임계값으로 PASS 여부 저장
  • 강한 관계를 weighted edge로 선택
  • 결정적 community, degree, centrality 계산

입력

  • 1단계 최신 확정 유형(LATEST_MASTER)
  • Target 테이블, 유의수준, 관계 강도, 샘플과 edge 제한

해석

  • 상관 통과는 인과관계나 최종 업무 규칙을 의미하지 않음
  • 기준 미달 관계도 다변량 수식 후보에 필요할 수 있음
  • 군집은 3단계 규칙 발굴의 선택적 보조 입력
UNIFIED_EDITING_RELATION → RELATION_PAIR · RELATION_NETWORK · MIXED_XAI_RELATION
3
M03003 · UNIFIED_EDITING_DISCOVER

자동 규칙 발굴

기존 Apriori·LASSO·Symbolic 분석 후 혼합형 실제 값·범위 트리와 수식을 발굴합니다. 최종 결과는 조건규칙과 수식규칙으로 조회하며 원래 발굴 방법과 검증 지표를 유지합니다. 과거 이상 후보 설명은 별도로 구분합니다. 같은 실행에 모델·출처를 구분해 저장하며, 혼합형 성공으로 기존 분석 실패를 덮지 않습니다. 결과는 사람이 검토할 후보입니다.

범주형 Apriori

  • 최소 support·confidence와 규칙 길이·조합 예산 적용
  • Oracle ML 연관 모델과 사람이 읽는 IF/THEN 요약 생성
  • lift와 표본 건수를 함께 저장

연속형 LASSO

  • 결측 중앙값 보정과 표준화
  • 교차검증 또는 계수 선택으로 중요변수 압축
  • 중요변수 결과와 최종 수식 채택 결과를 구분

Symbolic 규칙

  • 선형·강건·비율·다항 LASSO와 선택적 PySR 후보 비교
  • 안정성·설명력을 평가하고 Oracle-safe 수식으로 정규화
  • 수식과 R²를 규칙 후보로 저장

부분 완료

  • 범주형·연속형 하위 작업을 독립적으로 검토
  • 일부만 완료되면 성공 결과와 실패 메시지를 함께 반환
  • Flow Node는 FAILED와 검토 메시지로 기록될 수 있음
UNIFIED_EDITING_DISCOVER → ASSOCIATION_MODEL · ASSOC_RULE_SUMMARY · LASSO_FEATURE · SYMBOLIC_RULE · MIXED_XAI_RULES
4
M03004 · UNIFIED_EDITING_DETECT

규칙 위반 탐지

같은 Run의 기존 범주형·Symbolic 규칙과 혼합형 값·범위·수식 AST를 적용해 출처별 위반 행을 저장합니다. 규칙별 위반 건수는 겹칠 수 있어 고유 오류 행·셀 수로 합산하지 않습니다. 원본 데이터는 자동 수정되지 않습니다.

범주형 위반

  • 규칙 조건 일치 + 결과 NULL 또는 불일치 행 탐지
  • confidence·lift를 위반 점수의 보조 지표로 사용
  • 규칙별 저장·스캔 제한 적용

연속형 위반

  • 허용된 수식과 feature만 안전하게 평가
  • 실제값과 예측값의 상대·절대 오차 임계값 적용
  • 실제·예측·오차를 상세 결과에 저장

SAME_RUN 입력

  • 같은 Run의 연관 모델·범주형 규칙 요약
  • 같은 Run의 Symbolic 규칙
  • 규칙 부분, 허용 오차와 결과 제한

결과 해석

  • 퀵·상세 결과는 조건규칙·수식규칙을 20개씩 서버에서 조회하고 위반 상세는 선택 시 조회
  • SUCCESS이면서 0건은 정상 결과일 수 있음
  • FAILED이면 부분 완료 메시지로 유형별 성공 여부 확인
  • 실제 오류 수정은 M05002의 별도 작업 테이블에서 수행
UNIFIED_EDITING_DETECT → CAT_RULE_VIOLATION · SYMBOLIC_RULE_VIOLATION · MIXED_XAI_CANDIDATES

FLOW ORCHESTRATION & RESOURCE ROUTING

저장된 Job을 검증 가능한 DAG로 실행

M04001의 Flow는 단순한 그림이 아니라 저장·검증·실행 가능한 DAG입니다. 실행기는 검증된 위상 순서로 노드를 처리하고 각 상태와 출력을 동일한 Flow Run에 기록합니다.

01 · DESIGNJob 배치·연결

M03001~M03004에서 저장한 Job과 확장 리소스를 노드·엣지로 구성합니다.

02 · VALIDATE구조·계약 검증

순환, 역방향 단계, 포트·아티팩트와 SAME_RUN 입력을 확인합니다.

03 · BIND런타임 값 확정

Target, Result, 선행 출력, Run ID와 실제 파라미터를 결합합니다.

04 · EXECUTE실행 경로 선택

저장된 EXEC_SOURCE_TYPE에 맞는 어댑터를 한 개 선택합니다.

05 · MATERIALIZE결과 정규화

출력 계약과 메시지를 Run·Node 결과 아티팩트로 저장합니다.

M90001 · TARGET DB

내부 모델·실행 객체

등록된 프로시저, 패키지와 Oracle ML 모델을 서버 세션의 Target DB 연결에서 실행합니다. 객체명, 파라미터와 결과 계약이 실제 DB 정의와 일치해야 합니다.

주요 확인

  • 검증된 Target DB 연결과 등록 객체 ID
  • 대상 테이블·Run 바인드와 결과 테이블
  • 대용량 처리 시 병렬 자원, 범위와 커밋 단위
OML4PY · SQL API

OML Python 실행 경로

등록 리소스의 실행 방법에 따라 OML4Py Script Repository와 SQL API를 사용하고, 데이터프레임·행·테이블 결과를 표준 결과 계약에 맞춥니다.

지원 실행 계약

  • pyqEval, pyqTableEval, pyqRowEval
  • pyqGroupEval, pyqIndexEval
  • Target DB 권한, OML4Py 설치와 ACL 상태 확인
M90002 · API OBJECT REGISTRY

내부 Python API와 외부 JSON API

신규 통합 1~4단계는 WEB_API Job이며 INTERNAL_API 어댑터가 같은 WAS의 함수를 직접 호출합니다. 각 함수는 기존 Oracle 분석과 Python 혼합형 보강을 순차 수행합니다. 미등록 내장 Job은 저장된 계약으로 실행하며 EXTERNAL_API만 원격 HTTP 요청을 사용합니다.

M90002 기본 생성은 미등록 항목만 추가하고 기존 설정·비활성 상태를 보존합니다. M03001~M03004에서 자동 생성 Job을 열면 중앙 등록 ID가 없어도 저장된 모델·파라미터를 복원합니다.

검증 항목

  • method, endpoint, 입출력·저장 계약
  • 외부 응답의 시간·크기 제한과 유효 JSON 여부
  • EXTERNAL_API 인증 값은 런타임 입력이며 자동 비밀 조회가 아님

SKIPPED의존 조건을 충족하지 못했거나 실행 대상에서 제외되었습니다.실선 선행 노드는 SUCCESS가 필요하고, 점선 ON_COMPLETE는 선행 종료 후 진행할 수 있습니다.

SAFE OPERATION & SECURITY

실행 전후에 반드시 확인할 기준

데이터 에디팅은 Target DB의 실행 컨텍스트와 결과 이력을 다루므로, 선택 범위·실제 Run 파라미터·권한·반영 단계를 구분해 점검합니다.

01실행 전 컨텍스트

  • 현재 사용자, 역할과 Target DB를 확인합니다.
  • 프로젝트·시나리오·대상 테이블이 같은 범위인지 확인합니다.
  • Flow Validate에서 단계·포트·SAME_RUN 계약을 확인합니다.

02상태와 품질 분리

  • SUCCESS는 실행 종료이며 업무 승인이 아닙니다.
  • FAILED의 부분 완료 메시지를 유형별로 확인합니다.
  • 위반 0건은 오류가 아닌 정상 결과일 수 있습니다.

03수정·반영 안전성

  • 탐지 결과가 원본을 자동 수정하지 않습니다.
  • 수정본 효과 검증 후 버전 DML을 검증합니다.
  • 운영 반영 전 권한·실행 확인·감사 이력을 점검합니다.
